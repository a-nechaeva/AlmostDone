### Вход через Яндекс ID

Для входа через Яндекс Android передаёт OAuth-токен LoginSDK в `POST /api/v1/auth/yandex`
полем `oauth_token`. Backend проверяет токен у Яндекса и выдаёт собственную сессию
приложения. Формат запроса, ответа и ошибки описаны в [OpenAPI](openapi.yaml).

### Покупки под бюджет

`POST /recommendations/budget` возвращает план из существующего `best_purchases()`.
Алгоритм жадный: соблюдает бюджет, но не гарантирует глобально лучший набор покупок.
Ответ содержит `shopping_items`, `unlocked_recipe_ids` и `total_cost` в копейках.
Рецепты — альтернативы для приготовления, а не обещание приготовить все одновременно.
Если доступных покупок нет, возвращается `no_plan` с `total_cost=null`;
при недостатке данных без найденного плана — `insufficient_data`.
Запрос не меняет запасы и не сохраняет список покупок.

### Диетические ограничения

С PostgreSQL сервер применяет существующее представление `user_recipe_visibility`
к подбору, карточкам рецептов, избранному и рекомендациям покупок.
`GET /dietary-options` помечает как `supported` диеты, присутствующие в справочнике БД.
Причины скрытия содержат `excluded_diet` и стабильные ID ограничений;
`skip_optional` содержит ID необязательных ингредиентов, которые БД рекомендует исключить.
Готовность конкретной диеты смотрите в справочнике: отсутствующие в БД варианты остаются `unsupported`.
Флаг `diabetes` сохраняется, но остаётся в `unsupported_restrictions`;
расчёты при включённом флаге по-прежнему возвращают 503.
В режиме памяти SQL-правила недоступны, поэтому диеты остаются неподдерживаемыми.
Движок и правила SQL не изменены; дополнительные эндпоинты и миграции не требуются.

### Поиск рецептов и единицы количества

`filters.q` в подборе и рекомендациях покупок ищет подстроку в названии рецепта:
без учёта регистра, с нормализацией е/ё, Unicode и пробелов. Пустая строка не ограничивает выборку.
Фильтр применяется и к рецептам с неполными данными; остальные фильтры и сортировка сохраняются.

`GET /ingredients` сообщает допустимые единицы через `allowed_units`. Граммы доступны всегда;
миллилитры и штуки — при наличии соответствующего коэффициента в каталоге.
Миграция `002_ingredient_volume` добавляет `ingredients.grams_per_ml` и справочные коэффициенты
для воды, молока и нескольких растительных масел по [FAO/INFOODS](https://www.fao.org/4/ap815e/ap815e.pdf).
Это приближённые коэффициенты состава продуктов, а не универсальное равенство 1 мл = 1 г.
Количество в мл переводится в массу для расчётов и хранения; PostgreSQL хранит массу с точностью
0.01 г (округление половин вверх), а API сохраняет исходную единицу и значение после перезапуска.
Для продукта без коэффициента миллилитры не предлагаются; явный запрос такой единицы возвращает 409.

### Число порций и поиск ингредиентов

Параметр `servings` передаётся в существующие расчёты движка: количества, недостающее
и упаковки рассчитываются на запрошенное число порций. КБЖУ остаётся на одну порцию.
Снимки подбора и граф сохраняют выбранное число порций. При неполных исходных данных
неизвестные оценки по-прежнему возвращаются как `null`.
Поиск `GET /ingredients` принимает `q` длиной от 1 до 64 символов;
превышение ограничения возвращает 422, без обрезания запроса.
