
# Android «Почти готово»

Приложение входит через Яндекс ID и проверяет серверную сессию запросом
`GET /api/v1/me/state`.

## Запуск

Откройте каталог `mobile` в Android Studio, совместимой с AGP 8.13.2
(начиная с 2025.1.3). Установите SDK Platform 36 и выберите JDK 21 для Gradle
в Settings → Build, Execution, Deployment → Build Tools → Gradle.
Путь Android SDK хранится в локальном `local.properties`.

Выберите конфигурацию `app`, устройство с Android 7.0 / API 24 или новее и
нажмите **Run**. Приложение подключится к облачному API по адресу
`https://51.250.76.77`. APK можно собрать из каталога `mobile`.

```bash
./gradlew :app:assembleDebug

```

Для другого стенда передайте `-PalmostReadyApiBaseUrl=https://api.example.org`
или задайте свойство в `~/.gradle/gradle.properties`. При отладке через
`adb reverse` debug-сборка принимает `http://127.0.0.1:8000`, если на этом
порту запущен `server/`. Для своего экземпляра `server/` укажите в
`ALMOSTDONE_YANDEX_CLIENT_ID` публичный Client ID Android из `app/build.gradle.kts`.

APK находится в `app/build/outputs/apk/debug/app-debug.apk`. Для проверки
откройте приложение, войдите через Яндекс ID, перезапустите приложение, затем
завершите сессию в профиле.

## Запрос из репозитория

Передайте `AppContainer.api` в конструктор репозитория. Клиент сам добавляет
`/api/v1` и Bearer, при необходимости обновляет сессию и возвращает JSON
и заголовки. Например, для чтения версии состояния:

```kotlin
class StateRepository(private val api: AuthenticatedApi) {
    suspend fun version(): Long =
        requireNotNull(api.execute(ApiRequest("me/state")).json).getLong("state_version")
}

```

В запрос на изменение можно передать `ifMatch` и `idempotencyKey` из контракта.
Ответ возвращает `etag` и `retryAfter`. При ошибке HTTP те же заголовки и ошибка
OpenAPI доступны через `ApiHttpException`. При ответе 204 поле `json` равно
`null`.

## Автоматические проверки

Из корня репозитория с работающим Docker:

```bash
bash .github/android/check.sh

```

Команда выполняет все проверки. В GitHub Actions они запускаются параллельно
в пяти независимых jobs: `Unit`, `UI`, `Screenshots`, `Lint`, `Build`.
Ошибка одной проверки не отменяет остальные; у каждой собственный статус
и артефакты. Каждая job самостоятельно компилирует нужный код.

Отдельный набор можно запустить из корня:

```bash
bash .github/android/check.sh unit
bash .github/android/check.sh ui
bash .github/android/check.sh screenshots
bash .github/android/check.sh lint
bash .github/android/check.sh build

```

`Unit` выполняет обычные JVM-тесты, `UI` — методы с `@Category(UiSmoke::class)`,
`Screenshots` — методы с `@Category(Screenshot::class)`. Эти группы не пересекаются.
Новые UI и screenshot-тесты помечайте соответствующей категорией.
Локальные отчёты тестов сохраняются отдельно для каждой группы.

Тесты используют реальные ViewModel и экраны с fake-репозиториями,
фиксированным каталогом, подменой LoginSDK и HTTP-транспорта. Сервер
и аккаунты для автоматических проверок не нужны. Instrumented-тесты
из `androidTest` запускаются отдельно на устройстве.

Окружение рендера общее для CI и локального запуска: закреплённый digest
Linux x86 образа Ubuntu 24.04 с Temurin 21.0.9+10, Gradle Wrapper 8.13,
SDK 36 revision 2, build-tools 35.0.0 и platform-tools 37.0.1. Robolectric 4.16 использует SDK 36.
Зафиксированы ru-RU, UTC, начальные Android-часы 2025-01-01T00:00:00Z, экран
400 × 900 dp, density 2, светлая тема и font scale 1 / 1.5.
Compose синхронизирует анимации тестовыми часами; фотографии находятся в ресурсах.

Отчёты и APK этого запуска находятся в `.local/android-ci/build/`:
`reports/`, `test-results/`, `outputs/roborazzi/` и
`outputs/apk/debug/app-debug.apk`. Cache SDK и Gradle хранится рядом.
Первый запуск скачивает build-зависимости. Для него требуется доступ к Google,
Maven Central, Gradle Plugin Portal и Docker Hub.

Эталоны находятся в `app/src/test/screenshots/`. Для осознанного обновления
после изменения UI выполните из корня репозитория:

```bash
bash .github/android/check.sh :app:recordRoborazziDebug --tests '*AppSmokeTest.dishes*Screenshot'
bash .github/android/check.sh

```

Проверьте изображения и добавьте изменённые PNG в тот же коммит. CI выполняет
только сравнение: отличие или отсутствие эталона завершает прогон с ошибкой.
Восстановление эталонов из Gradle cache отключено при проверке; каталог PNG
в CI доступен контейнеру только для чтения.
В артефактах сохраняются отчёты, expected, actual и diff; срок хранения — 5 дней.

На каждом PR служебная job `Android changes` определяет изменённые файлы.
Пять Android-проверок запускаются только при изменениях кода в `mobile/`,
его workflow или скриптов `.github/android/`. Markdown в `mobile/` и backend
не запускают Android-проверки. На push в `main` workflow по-прежнему ограничен
этими Android-путями.

Итоговый статус `Merge gate` ожидает все пять отдельных jobs и проверяет каждый
результат через `needs`, без агрегирования matrix. При ошибке, отмене,
неожиданном пропуске Android-проверок или ошибке определения файлов он красный.
Если Android не затронут, пять проверок пропускаются, а `Merge gate` проходит.
Для определения изменений используется полный Git diff без ограничения числа
файлов; удаление и перенос файлов из Android также требуют проверок.

Для защиты `main` владелец открывает Settings → Rules → Rulesets и создаёт
branch ruleset `main-protection` для ветки `main`. Включает Require a pull request
before merging (approvals могут быть 0) и Require status checks to pass, добавляя
**только `Merge gate`** с источником GitHub Actions. Сначала статус должен появиться
в успешном PR-прогоне. В Bypass list можно добавить Repository admin с режимом
For pull requests only для явных исключений через PR. Затем включить Active.
Не назначайте пять условных Android-проверок обязательными отдельно.
Настройки защиты ветки этим workflow не меняются.

## Структура

- `app` — Application и контейнер зависимостей на время жизни приложения.
- `domain` — модели, интерфейсы репозиториев, подбор и расчёт докупки; без Android,
  Compose, HTTP и SQL.
- `data` — клиент API, хранилище сессии, локальные реализации Room и Preferences DataStore.
- `feature` — ViewModel, состояния и экраны по сценариям.
- `ui` — тема, форматирование и общие компоненты.
- `navigation` — четыре вкладки и вложенные экраны, передача ID рецептов.

Поток: действие экрана → ViewModel → репозиторий → локальное хранилище → Flow →
UiState → экран. Состояние собирается с учётом lifecycle. UI не обращается
к базе и не рассчитывает стоимость или пригодность блюда.

DataStore сохраняет пару серверных токенов и их сроки одной записью.
При выходе пара удаляется. Резервное копирование отключено.

## Локальные сценарии в тестах

- Количества задаются в граммах, миллилитрах или штуках. Неизвестное количество
  хранится отдельно; разные единицы автоматически не преобразуются.
- Повторное добавление продукта суммирует совместимые количества по ID.
  Добавление к неизвестному количеству сохраняет неизвестный итог.
- Число порций меняет ингредиенты; КБЖУ подписано на одну порцию.
- Стоимость докупки учитывает целые упаковки и известный остаток дома.
  При неизвестном количестве или отсутствии цены показывается «Нет оценки».
- Список покупок суммирует потребности всех выбранных рецептов и вычитает запас
  дома один раз. Повторное добавление того же рецепта обновляет число порций.
- Предложенная отдельная упаковка задаёт минимальный объём покупки; она
  не дублирует ту же потребность из рецептов.
- Отметка «куплено» не меняет кладовую. Кнопка «Добавить купленное домой»
  переносит количество целых упаковок одной транзакцией.
- Ограничения профиля обновляют подбор. Явное несовпадение скрывает рецепт;
  неполные сведения выводятся отдельно. Для диабета и диетического стола
  критерии не утверждены, поэтому соответствие остаётся неизвестным.
- Ранее выбранные покупки сохраняются при изменении профиля; несоответствие
  выбранных рецептов новым ограничениям показывается предупреждением.
- Лучшая одиночная покупка открывает альтернативные варианты блюд, а не обещает
  одновременное приготовление всех вариантов из одного запаса продуктов.

## Граф во вкладке «Блюда»

Переключатель «Список / Граф» меняет представление общего подбора. Поиск,
фильтры времени, калорийности, способа приготовления и доступности, продукты
дома и ограничения профиля действуют в обоих представлениях.

Граф показывает лучшую одиночную покупку и блюда, для каждого из которых
достаточно этой упаковки. Это альтернативы, а не общий план приготовления.
Если подходящей покупки нет или количество/ограничения требуют уточнения,
экран предлагает изменить фильтры или вернуться к списку. Цена берётся
из демонстрационного каталога; граф не рассчитывает новый бюджет.

Нажмите на блюдо, чтобы открыть рецепт; Back возвращает к графу с теми же
фильтрами. «Добавить в покупки» сохраняет упаковку в общем списке покупок.
Запас дома при этом не меняется. Повторное добавление той же упаковки
не создаёт дубликат. Представление и фильтры сохраняются в состоянии экрана.

UI-проверки включают переключение, общий поиск и фильтры, рецепт и системный
Back, общие покупки и повтор после ошибки. Screenshot-проверки дополнительно
покрывают граф с обычным и крупным шрифтом, пустой подбор, отсутствие связей,
загрузку и ошибку чтения. Все эти проверки используют fakes без backend и OAuth.
