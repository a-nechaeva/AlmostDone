# База данных

`schema.sql` создаёт пустую БД со справочниками, каталогом, пользователями и
таблицами серверного состояния. `seed.sql` — отдельный дамп каталога со старой
схемой: после его загрузки нужно применить миграции. Эти файлы — альтернативные
способы начальной установки, не запускайте их последовательно на одной БД.

## Миграция существующей БД

Сделайте резервную копию. После существующей схемы или загрузки `seed.sql`:

```sh
psql -X --dbname "$ALMOSTDONE_DATABASE_URL" -v ON_ERROR_STOP=1 -f db/migrations/001_server_state.sql
```

Миграция применяется **один раз**, целиком в транзакции.
Она не удаляет и не перезаписывает существующие аккаунты, каталог или кладовку. В `user_api_state`
добавляется начальная запись для каждого существующего пользователя. После
создания новой БД через обновлённый `schema.sql` миграция уже включена.
Проверить применённые миграции:

```sql
SELECT version, applied_at FROM public.api_schema_migrations;
```

Если таблицы ещё нет, миграция не применена. Повторный запуск завершится ошибкой
и откатом; это не механизм исправления частично изменённой вручную схемы.
Пользователю приложения нужны права на чтение/запись новых таблиц и использование
identity-последовательности `user_identities`; миграцию выполняет владелец схемы.

## Новые таблицы

| Таблица | Назначение |
| --- | --- |
| `user_identities` | Уникальная связь `(provider, provider_subject)` с `users.id` |
| `auth_sessions` | Один вход пользователя, абсолютный срок действия и отзыв |
| `auth_tokens` | История пар токенов с SHA-256 хешами, сроками, использованием refresh и отзывом |
| `user_api_state` | Версия состояния, `diabetes` и исходные количества/единицы кладовки в `pantry_display` |
| `api_idempotency` | Отпечаток запроса, результат и срок хранения ключа в рамках пользователя и операции |
| `api_resources` | JSON снимков подбора, курсоров и результатов распознавания с TTL |
| `recognition_imports` | Постоянная отметка однократного импорта чека |
| `api_schema_migrations` | Применённые изменения схемы |

Индексы поддерживают поиск по хешам токенов, пользователю и сроку истечения.
Удаление пользователя каскадно удаляет принадлежащие ему записи. Отметки импорта
не привязаны внешним ключом к временным ресурсам: очистка результата распознавания
не должна разрешать повторное пополнение кладовки.

## Как сервер использует таблицы

При заданном `ALMOSTDONE_DATABASE_URL` сервер использует SQL-репозиторий вместо
`MemoryRecords`. Без этой переменной остаётся демонстрационный режим в памяти.
В `user_api_state.state_hash` хранится отпечаток данных пользователя для
обнаружения изменений другими SQL-клиентами. Сроки access и refresh независимы.
В репозитории реализованы следующие правила:

- Проверять владельца, срок и отзыв сессии при каждом запросе. Блокировать пользователя
  при refresh, атомарно помечать старый refresh использованным и выдавать новую
  пару. Повтор использованного refresh отзывает всю сессию. Не удалять историю
  токенов, пока в сессии остаётся действующий access или refresh; новые пары не
  продлевают абсолютный срок refresh.
- Хранить только хеши случайных токенов, не OAuth-токен Яндекса. Не сохранять
  ответы авторизации в `api_idempotency`. UUID сессий/ресурсов создаёт приложение.
- Обновлять данные пользователя, `state_version`, результат идемпотентности и
  отметку импорта в одной транзакции. Уникальные ключи не заменяют блокировки.
- При регистрации создавать `user_api_state`. Для существующих OAuth-аккаунтов
  привязывать `user_identities` после проверенного входа, сохраняя прежний user ID:
  исходный идентификатор Яндекса невозможно восстановить из технического логина.
- В `pantry_display` хранить отображение `{ingredient_code: {value, unit}}` для
  известных количеств; сверять его с массой в `user_pantry`. Неизвестное количество
  по-прежнему хранится как `user_pantry.qty_g = NULL`. Обновлять обе записи вместе.
- Сериализовать модели движка в JSON для `api_resources`; не хранить фотографии.
  Сроки хранения задаёт приложение. Для истёкшего снимка сохранять данные владельца
  достаточно долго, чтобы вернуть `snapshot_expired`, а не случайный `not_found`.
- При очистке удалять истёкшие данные. Отметки импорта сохранять отдельно от TTL
  ресурсов. `updated_at` изменяется приложением при записи состояния.
